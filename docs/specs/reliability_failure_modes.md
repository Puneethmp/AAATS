## Severity legend

- **S1 — Silent.** Failure happens with no operator-visible signal. Discovered days later via PnL surprise, audit, or accidental log inspection. Highest priority because the system *appears* healthy. Examples: heartbeat schema mismatch where monitor reads stale data and never alerts; v6 stack sitting in -15.5% HALT for 3+ days while Docker reports "healthy".
- **S2 — Noisy.** Failure emits log/alert noise but no actionable signal — or noise drowns the actionable signal. Operator either dismisses it or has to triage by hand. Examples: HALT CRYPTO logged 479x in 24h while trades still execute; literal `%s %d %.2f` printed in production logs.
- **S3 — Catastrophic.** Failure halts trading, drains state, or trips kill-switch in a way that requires manual intervention to recover. Operator notices immediately but recovery is multi-hour. Examples: container restart loses cycle counter / one-shot init flags; -42.6% drawdown HALT with reconciler dual-source ambiguity blocking unhalt.

## Ranking heuristic

Rows are ranked by **operator-impact score** = `(silent_weight × 3) + (recurrence_weight × 2) + (recovery_cost_weight × 1)`, where:

- `silent_weight` = 1 if S1, 0.5 if S2, 0.25 if S3 (silent failures hurt most because they accumulate undetected).
- `recurrence_weight` = 1 if the failure mode has bitten in two or more dated incidents in the source docs; 0.5 if one; 0.25 if forecasted/latent only.
- `recovery_cost_weight` = 1 if recovery requires `ssh aaats@` + `docker exec` + multi-step state surgery; 0.5 if requires container restart only; 0.25 if logs-only / informational.

Ties broken by directly-cited "has bitten" evidence in the NO-GO doc (treated as authoritative for operator-lived pain).

## Cross-cutting observations

Patterns visible when reading the catalog as a whole:

1. **Silent (S1) failures dominate the top of the ranking.** Of the top-10 rows, 6 are S1. The operator's lived pain ("system is breaking but I don't notice for weeks") is structurally caused by detection gaps, not by catastrophic crashes. Track D's bias toward "make failures noisy" (D.2 watchdog, D.4 digest) is correctly targeted; what's NOT targeted is the "engine ERROR-spam drowns real signal" failure mode (row 12) which is the opposite — too much noise, no signal.

2. **Schema-drift / dual-source-of-truth is the most common root cause.** Rows 1, 4, 6, 8, 9, 11, 12, 17, 18 all trace to either (a) a writer + reader pair using different schemas/conventions, or (b) two storage locations claiming to be canonical (state-file vs DB; paper_positions.json vs paper_trades.db; risk_engine state vs engine log). D.3 (schema-drift assertions on startup) closes ~9 of 23 rows by construction. This is the highest-leverage Track D phase.

3. **Docker `healthy` is a load-bearing lie.** Rows 3, 21, and (implicitly) 2 all share the pathology: the container is "healthy" by Docker's healthcheck definition while the trading strategy is HALTED, idle, or wedged. Every reliability detector that relies on `docker ps`-style health is unreliable for this codebase. D.2's watchdog must hang off the trade-loop heartbeat file, not the Docker healthcheck — the D.2 spec already captures this; flagged here so it doesn't drift.

4. **The "halt_on_critical=False" pattern recurs.** Row 10 was the explicit instance, but rows 8 (C5b suppression by halt-at-source), 9 (dust-filter silencing), and 12 (reconciler logs HALT severity but trades continue) all share the underlying shape: a real signal exists in the system but is suppressed somewhere downstream to keep the operator from being woken up. Each individual suppression is principled. The cumulative effect is that "no alert fired" no longer means "nothing was wrong." D.4's daily digest is the cleanest cross-cut here because it forces the suppressed-but-real state into a single readable surface every morning.

5. **Three rows are NOT closed by any D.x phase.** Rows 5, 7, 16, 22 (and partly 6, 11, 14, 15) are closed by Track A (live-flip rebuild) or by unified-ledger work. Listed in the table as `GAP — propose D.6?` where applicable (rows 7, 17, 22). The candidate D.6 scope: exporter-target watchdog (row 7) + linter/deny-list for known anti-patterns (rows 17, 22). All three are small (≤1 session each); could be bundled into a single D.6 if operator wants a clean Track D close-out beyond D.5's 30-day soak.

6. **Live-flip mechanism gaps (rows 5, 14, 15, 16) are Track A's domain, not Track D's.** They're catalogued here because the NO-GO doc cited them as operator-visible failure modes, but Track D's parallel-safety promise depends on NOT touching `risk/engine.py`, `validate_env.py`, or compose's `SYSTEM__TRADING_MODE`. These rows are mapped to "GAP — closed by Track A.x" and remain blockers for the live-flip critical path independently of D.5's soak metric.

7. **The 2026-05-18 -$2.81 single-day blowup (9-of-9 C3 losers) is a strategy correctness issue, NOT a reliability issue, and is therefore not catalogued here.** Tracked in [`2026-05-22_live_flip_rebuild_plan.md`](../decisions/2026-05-22_live_flip_rebuild_plan.md) §"Diagnostic appendix" item C and owned by Track B. Calling it out so future readers don't expect to find it in this catalog.

8. **No row is closed by D.5 directly.** D.5 is a soak-time validator, not a fix. Every row that says "D.x closes it" means D.1–D.4 implementation. D.5 then validates that the closed rows stay closed for 30 calendar days under real load. If a new failure mode surfaces during the D.5 soak, it gets added here and the soak clock resets per the addendum's exit criteria.
