**Plot**: ![D1 voter correlation heatmap](d1_corr_heatmap.png)

### Plain English
The 6 voters (`vote_ema`, `vote_rsi`, `vote_momentum`, `vote_vwap`, `vote_bollinger`, `vote_macd_hist`) are genuinely independent. The largest correlation (0.65, between `vote_ema` and `vote_momentum`) is below the 0.85 redundancy threshold, and the average is well below 0.70. **The 6-vote consensus system is doing real work** — it's not 6 wrappers around the same underlying signal. The voters disagree often enough that requiring consensus is a meaningful filter.

The Cohen's κ values (averaged 0.12) are low because the categorical signals are dominated by HOLD in this regime — kappa is conservative when one class is heavily oversampled. The Pearson correlation on numeric scores (signal × confidence) is the more informative metric here, and it confirms independence.

**This means**: when 6/6 voters say HOLD, that's not artificial unanimity — it's 6 independent indicators all reaching the same conclusion.

## D2 — ML Confidence Distribution Check

**Verdict**: ⚠️ **INCONCLUSIVE** (per protocol — live N < 500)

| Metric | Live (logs) | Replay (90d/4h) |
|---|---|---|
| N | 91 | 2,802 |
| Mean | **0.299** | **0.850** |
| Std | 0.050 | 0.101 |
| Live mean's percentile in replay distribution | **0.3%** | — |
| KS test | NOT RUN (underpowered, N < 500) | — |

**Recorded training set size** (from `training_meta.json`): 17,020 samples
**Validation accuracy at training time**: 0.551 (slightly above coin-flip)
**Model trained**: 2026-05-07T18:45 UTC (~2 days old)

**Plot**: ![D2 confidence distribution](d2_conf_distribution.png)

### Plain English
**The headline number (live mean at 0.3rd percentile of replay) is partly an artifact of selection bias, not a true distribution shift.** Live confidence values are only logged when the ML gate fires — and the gate only fires when the consensus signal is non-HOLD AND the ML confidence is below 0.40. So the 91 live samples are **deliberately selected from the bottom of the distribution by design**. Of course they cluster low.

What we **can** say:
- The model on disk produces a wide confidence distribution (μ=0.85, σ=0.10) when run on 90 days of unfiltered historical bars — this is sensible. A trained classifier should be confident on most data points.
- The 0.40 gate threshold has a clear interpretation: reject when the model is in the bottom ~5% of its own confidence range.
- We do **NOT** know whether the live distribution is truly out-of-distribution from the training set. To answer that we need either (i) the actual training X/y matrix saved, OR (ii) ≥500 unbiased live confidence samples (ML conf logged on every prediction, not just gate-fires).

### Recommendations (data collection only — not code changes)
- Extend Docker log retention so 91 samples doesn't reset on every container restart. Add `logging:` driver `max-size: 100m, max-file: 10` to `docker-compose.yml`.
- Log ML conf for **every prediction** (success AND skip), not just gate-fires. This eliminates selection bias.
- Re-run D2 in 2 weeks once ≥500 unbiased samples accumulate. Then the KS test is valid.

## Known Limitations

This section documents what the diagnostics did **not** test, what assumptions could be wrong, and what could invalidate the findings.

### D1 — Replay assumptions
- Replay used `_rule_regime` (the fallback) instead of the HMM regime detector. The HMM is cache-only and the cache is empty for historical bars. So the regime labels in replay are derived from ADX/EMA/ATR rules only — not from the trained HMM that may run live. **Implication**: voters that take regime as input may behave differently in production if the HMM produces materially different labels than the rule fallback. We can't quantify this without saving the HMM cache.
- Replay computes features locally (RSI/MACD/EMA/etc.) using standard formulas. If the live `indicators/features.py` uses a slightly different formulation (different alpha, different window), feature values could differ and produce different votes. The replay's vote distributions match the spirit but not necessarily byte-for-byte the production output.
- Voter pure-function statelessness was code-inspected (no globals, no class state) but not formally property-tested.

### D2 — Statistical power
- N=91 is too small to bound the live distribution mean to better than ±σ/√91 ≈ ±0.005. Comparison to a 2802-sample replay is not a valid hypothesis test.
- The selection bias (live conf only logged at gate-fire) means even ∞ live samples wouldn't directly compare to an unbiased replay distribution.
- The "replay distribution" is not the same as the "training-time distribution". The model was trained on 17,020 samples we don't have access to. Replay on 90d/4h is a proxy that **assumes the 90-day price regime is similar to the training-set regime** — this assumption is itself untested.
- Re-run with ≥500 unbiased samples + KS test before drawing strong conclusions.

### D3 — Snapshot caveats
- All p-values, correlations, and z-scores are point-in-time. SOL/AVAX passing the gate today says nothing about whether it will pass tomorrow. The 30-day rolling EG history for BTC/ETH (1.9% of windows tradeable) shows pairs **drift in and out of cointegration**.
- The Engle-Granger test assumes I(1) series — close prices generally satisfy this, but extreme moves (e.g., a hard fork, a delisting) could violate the assumption and inflate p-values.
- We did NOT compute rolling p-value series for the other 14 pairs — that's a follow-up if you want pair-stability analysis. SOL/AVAX could itself be a recent cointegration that won't last.
- The hedge ratio used for z-score is OLS, not Kalman. A Kalman-filtered hedge ratio could change z-scores meaningfully.

### What is NOT tested by any of D1-D3
- **Look-ahead bias in the ML model**: features used at train time may include information that wouldn't have been available at the trade decision moment. Not checked. Would require training-set inspection.
- **Label leakage**: if labels were generated from forward returns and any feature contains forward information (e.g., a moving average computed including the bar being predicted), val_acc=0.551 may be optimistic. Not checked.
- **Walk-forward stability**: model performance may have degraded out-of-sample. The val_acc=0.55 is from a single time-series split at training time, not a walk-forward expanding window.
- **Slippage / fill assumptions**: no diagnostic looks at whether paper-trade fills are realistic. If the bot eventually trades and shows P&L, it could be inflated by ignoring slippage and partial fills.
- **Voter weight calibration**: D1 verifies independence but does NOT check whether the per-voter confidence values are well-calibrated (e.g., does a 0.78 conf BUY actually win 78% of the time?).
- **Regime detector accuracy**: we used the fallback in replay; we did not benchmark the HMM regime detector against a held-out labeled set.

## Final Recommendations (Diagnosis Only)

**No code changes proposed.** What this report shows:

1. **The 6-vote consensus is functioning as designed** — it's not redundant, voters genuinely disagree. When all 6 say HOLD, that's a real signal, not artificial unanimity. **No reason to relax consensus thresholds.**

2. **The ML gate at 0.40 has a clear interpretation** — it rejects predictions in the bottom ~5% of the model's typical confidence range. Whether this threshold is *right* requires either (a) saving the training X/y matrix to disk for direct comparison, or (b) waiting 2+ weeks for ≥500 unbiased live samples to enable a valid KS test. **Don't tune the threshold based on current data — there isn't enough.**

3. **Stat-arb is the area where revisiting is justified.** BTC/ETH was historically a weak pair (cointegrated only 1.9% of the time over 90d) — the live system's "waiting for the pair to come back" logic is waiting for something that wasn't reliable to begin with. **SOL/USDT–AVAX/USDT is currently passing all health gates and is being ignored.** This is a pair-selection question, not a threshold question.

4. **Data collection gaps to address before next diagnostic**:
   - Configure Docker log rotation (`max-size: 100m, max-file: 10`) so logs survive container recreation.
   - Log every ML confidence value (not just gate-fires) to enable unbiased distribution analysis.
   - Persist the training X/y matrix (or at least a hold-out sample) so D2 can do a proper distribution comparison.
   - Optional: log per-voter votes to a structured file (not just the consensus) — would make future D1 runs cheaper and more authentic.

**What NOT to do based on this data**: don't lower ML threshold, don't lower consensus threshold, don't disable F&G filter. The gates are blocking entries because the indicators are correctly cautious in the current regime. The finding is *which strategy is structurally limited (stat-arb pair selection)*, not *which gate is too tight*.
